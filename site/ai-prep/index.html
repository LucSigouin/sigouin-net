05Deploy and verification discipline

Done means proven

"Done" means a command passed. Not that an AI said so.

  1. Write the scorecard before any worker exists

    4 to 6 plain criteria. It becomes every worker's self-check.

  2. Write the check, then break things on purpose

    Plant a bug and confirm the check goes red. A check that has never failed has proven nothing.

  3. Each worker builds in its own folder

    Two workers never edit the same files. It writes a report of what passed and what it couldn't verify.

  4. The canvas runs the check when the worker says done

    Pass and it counts. Fail and the error goes back to the worker. 3 attempts.

  5. Deploy

    Publishing always asks me first.

  6. Prove it on the live site

    Fetch the served file, hash it, match it to the local copy, and test the change on the live site. Then I say live.

Times the inspector said no
BLOCKED

A password left in the code. The check refused "done" on four workers because a password placeholder was left in the code.

BLOCKED

A fix that broke its own page. A security fix was sent back because the new login check locked out the console's own page.

CAUGHT

An overclaim. A worker said a marker was on every chart. It was on 5 of 6.

BLOCKED

A CSS fix at work bounced twice before it counted.

LEARNED

A check that cheated. In one round a check rebuilt the very file it was judging. Now every output is frozen and hashed first, and checks are read-only.

06Guardrails and the trust story

Specific destructive commands are blocked

Even when I let agents run without asking me each step, some doors stay locked. I tested that the locks hold.

30

Destructive commands blocked

Wiping folders, force-pushing code, resetting history, formatting disks, piping a download straight into a shell. Blocked outright.

7

Publish actions ask a human

Pushing code, opening a pull request, a release, a package publish, two kinds of deploy. Each one needs my OK, every time.

Read-only

Keys get cut to read-only

I prove it by asking the API (the door other software uses) for the key's own role. A security console account went from Admin to Viewer. A backup tool's key gets refused on every write.

0

Hidden agents

Every AI worker is a visible window on my canvas. A rule blocks the invisible kind. I can watch, type into, or stop any of them.

0

Secrets in chat or code

Keys live in local files, never in code, chat or the service list. Each one has a dated test call on record.

6 of 8

Add-on tools rejected

Before installing anything, research workers vetted 8 tools. One rewrote command output silently. One pulled outside text live with no filter. Nothing got installed during the review.

Tough questions

Isn't this just prompting?

Prompting is asking one AI one question. I run a process around it: a scorecard written first, separate workers, a check that must pass, and a live re-check before I say done.

The prompt is the easy part. The hard part is knowing when the AI is wrong, and that's what the checks are for.

Proof96% of over 600 tasks carried an automatic check. 60 saved proof files document checks tested with deliberate failures.

What if the AI is wrong?

It will be, sometimes. That's the whole design. Nothing counts until a check passes. Before I trust a check, I break the thing on purpose and make sure it goes red. 60 of those tests are on file.

A wrong answer gets bounced back to the worker with the error. After 3 tries a human decides.

ProofThe gate refused four workers because a password placeholder was left in the code. A reviewer caught a claim that was true on 5 of 6 charts.

What about security and our data?

Least access first. Keys get cut to read-only, and I prove it by asking the API for the key's own role. My work dashboard team built on fake data only.

30 destructive commands are blocked outright. Anything that publishes asks me first. Keys live in local files, never in chat or code.

ProofIn the August work audit, 5 of 10 sets of keys could write on the first run. Now 4 remain and all 4 were verified read-only.

Why you instead of a dev shop?

I'm an IT operator who builds. I already work inside the tools IT companies and small businesses run on: ticketing, device management, endpoint security, accounting.

Fixed scope, so you know the ceiling. And the speed is real: TeeTimes went from brief to live in 3 days.

ProofThe security move at work: 108 new sites and 90 security rules set up by script, 0 failures.

What if an AI vendor changes prices or cuts you off?

Don't trust it. Trust the checks. The builds I'd show you ship with tests, and before I trust a check I break the thing on purpose and make sure it goes red.

Spawn three honest workers

Paste the three commands one after the other. What each check looks at:

  • Writer: the file exists and is 8 lines or fewer.
  • Coder: at least 3 test functions, and the unit tests pass.
  • Researcher: at least 3 lines with a web link. It doesn't check that the prices are right.
# Writer
cnvsctl spawn-agent --agent claude --name Writer --prompt "Write a 5-line plain-English explanation of a quality gate for a small business owner into /Users/ls/Claude-Workspace/cnvs/demo-live/a-summary.md. Then report done to CNVS." --verify "test -s /Users/ls/Claude-Workspace/cnvs/demo-live/a-summary.md && [ \$(wc -l < /Users/ls/Claude-Workspace/cnvs/demo-live/a-summary.md) -le 8 ]"
# Coder: leave it as a visible terminal, do not add --headless
cnvsctl spawn-agent --agent codex --name Coder --prompt "In /Users/ls/Claude-Workspace/cnvs/demo-live/b/ write invoice.py with a function total_with_tax(subtotal, rate) that rounds to cents, and test_invoice.py with at least 3 unittest cases. Run the tests. Then report done to CNVS." --verify "[ \$(grep -c 'def test' /Users/ls/Claude-Workspace/cnvs/demo-live/b/test_invoice.py) -ge 3 ] && python3 -m unittest discover -s /Users/ls/Claude-Workspace/cnvs/demo-live/b"
# Researcher
cnvsctl spawn-agent --agent grok --name Researcher --prompt "Find 3 published 2026 price ranges for a small-business AI workflow audit. Write them with their source URLs to /Users/ls/Claude-Workspace/cnvs/demo-live/c-research.md. Then report done to CNVS." --verify "[ \$(grep -c 'https://' /Users/ls/Claude-Workspace/cnvs/demo-live/c-research.md) -ge 3 ]"

Three different AI tools, three separate jobs, three separate files. A writer, a coder, a researcher. Each one gets its test attached when I hire it, not after.

Spawn the one that lies

Its check: the file exists and contains the line DONE-CHECK.

cnvsctl spawn-agent --agent claude --name Liar --prompt "This is a live demo of a quality gate. Step 1: report done to CNVS right now with the note 'all finished', before creating any file. Step 2: when CNVS hands you the failure, create /Users/ls/Claude-Workspace/cnvs/demo-live/d-checklist.md with a 5-item pre-launch checklist for a small website, ending with a line that says DONE-CHECK. Then report done again." --verify "test -s /Users/ls/Claude-Workspace/cnvs/demo-live/d-checklist.md && grep -q DONE-CHECK /Users/ls/Claude-Workspace/cnvs/demo-live/d-checklist.md"

This fourth one I told to cheat on purpose. It's going to say "done" without doing anything. I'm telling you up front so nobody thinks I staged a lucky failure.

0:45

Point at the canvas

Zoom out so all four terminals show: cnvsctl zoom-to-fit

Four AIs working at the same time, and I can see every one of them. Nothing runs hidden. In my full setup a status board flags any worker that goes quiet for 10 minutes, and I decide what happens. Nothing gets killed automatically.

1:05

The gate rejects the lie

Point at the Liar terminal. When it reports done, CNVS runs its check, gets exit 1, and hands back the failure with a note like "Fix the failure and run done again (2 attempts left)." The live wording may differ. Don't promise when it will retry.

It said "all finished". The check ran, the check failed, and the job bounced straight back. Its word counts for nothing. Only the check counts. When it says done again, the same check runs again.

1:25

Close the loop

Once the workers finish, run cnvsctl tasks and point at the done states.

That's the whole idea in one screen. Parallel work, a test on every job, and "done" means the test passed. I've run over 600 jobs this way since August.
